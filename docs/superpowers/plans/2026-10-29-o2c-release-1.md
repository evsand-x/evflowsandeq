# O2C Release 1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Deliver the simplified Office Order-to-Cash flow `Sales Order → Surat Jalan → Invoice`, with payment support kept after invoice and with Surat Jalan issuance acting as the delivery, stock, revenue and HPP event.

**Architecture:** Keep the modular monolith and reuse the existing SO, stock movement, posting, numbering, policy, audit and permission services. Add a focused Surat Jalan aggregate and command path rather than routing the simplified flow through automatic allocation, picking, packing and POD. Invoice creation consumes one issued Surat Jalan and remains idempotent.

**Tech Stack:** Next.js/React/TypeScript, NestJS/TypeScript, PostgreSQL/Prisma, TanStack Query/Table, shared contracts and design tokens, Vitest/integration tests.

**Spec:** `docs/superpowers/specs/2026-10-29-o2c-release-1-design.md`

## Global Constraints

- Surat Jalan draft never mutates stock or ledger state.
- Issuing Surat Jalan records handover evidence and atomically creates stock movement plus revenue/HPP posting.
- Invoice can be created only from an issued Surat Jalan and at most once per Surat Jalan.
- SO lines can be delivered cumulatively across multiple Surat Jalan documents, never above ordered quantity.
- Termin/TOP is selected on SO from active Setting values, snapshotted, and inherited by Invoice.
- Tax and freight defaults are editable configuration; no hardcoded business rates or accounts.
- Every operational action has independent server authorization and company/data scope checks.
- Posted documents are immutable; correction uses the existing reversal/adjustment controls.
- Money and quantity calculations use Decimal/PostgreSQL numeric types.
- No new preview route, simulated principal, or runtime fixture is introduced.

## Review Focus

- Two concurrent Surat Jalan issues for the same SO line must not exceed ordered quantity or available stock; cover with a transaction race test in Task 2.
- Retrying issue or invoice after a lost response must not duplicate movement, posting, number or AR; cover with idempotency tests in Tasks 2 and 3.
- A user with SO permission but no outbound or invoice permission must receive 403 at the API; cover in Task 1 and Task 2.
- A changed Setting after SO creation must not change the SO/Invoice TOP, tax, freight or account snapshot; cover in Task 2 and Task 3.
- A Surat Jalan with missing/invalid handover evidence, closed period, expired/quality-held stock or excessive quantity must be rejected without partial writes; cover in Task 2.
